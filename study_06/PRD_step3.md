# PRD 3단계: 사용자 프로필과 레시피 저장 (study_06)

- 작성일: 2026-10-29
- 상태: 초안 (구현 전)
- 선행 조건: 1단계 (`PRD_step1.md`), 2단계 (`PRD_step2.md`) 완료

## 1. 배경 및 목적

추천받은 레시피 중 마음에 드는 것을 저장해 두고 나중에 다시 보고 싶다. 또 알레르기나 싫어하는 재료가 있는 사람은 매번 조건을 말하지 않아도 추천에 반영되어야 한다. 3단계에서는 **사용자 프로필**을 만들고, 프로필별로 **레시피를 저장**하며, 프로필 정보를 2단계 레시피 추천에 반영한다.

한 기기(가족이 함께 쓰는 노트북·태블릿 등)에서 여러 명이 쓰는 상황을 기본으로 한다.

## 2. 범위

### 2.1 포함 기능

- 프로필 만들기 / 수정 / 삭제 / 전환 (한 기기에서 여러 프로필)
- 프로필 항목: 이름, 아바타 이모지, 알레르기, 식단 유형, 싫어하는 재료, 매운맛 선호, 보유 조리 도구, 기본 양념 목록, 기본 인분
- 프로필 정보를 레시피 추천 프롬프트에 반영 (2단계 확장)
- 알레르기 재료가 들어간 레시피를 서버에서 한 번 더 검사해 경고 표시
- 레시피 저장 / 저장 취소 (2단계 카드·상세 화면의 ♡ 버튼)
- 저장한 레시피 목록: 검색(이름·재료), 정렬(최근 저장순/별점순/조리 시간순), 상세 보기, 삭제
- 저장한 레시피에 메모, 별점(1~5), "만들어 봤어요" 표시
- 데이터 백업: JSON 파일로 내보내기 / 가져오기

### 2.2 명시적 제외 (Out of Scope)

- 회원가입·로그인·비밀번호 (한 기기 안에서 프로필만 구분, 보안 목적 아님)
- 다른 기기와 동기화, 레시피 공유 링크
- 서버 데이터베이스 (아래 3.1 참고) — 후속 과제
- 저장한 레시피 다시 생성(AI로 수정)하기

## 3. 기술 구성

### 3.1 저장 위치 결정: 브라우저 localStorage

| 선택지 | 장점 | 단점 |
|---|---|---|
| **localStorage (선택)** | 서버 코드 변경 최소, 로그인 없이 바로 사용, 이전 study와 같은 방식 | 브라우저·기기를 바꾸면 데이터가 안 따라감, 용량 약 5MB |
| 서버 JSON 파일 / SQLite | 기기를 바꿔도 같은 서버면 유지 | 로그인이 없으면 누구 데이터인지 구분 불가, 서버 구현량 증가 |

로그인 없이 "한 기기에서 프로필 구분"이 목표이므로 localStorage로 충분하다. 기기 이동은 **JSON 내보내기/가져오기**로 해결한다. 레시피 1개가 약 2~3KB이므로 저장 레시피 1,000개 정도까지 용량 문제는 없다.

서버는 프로필 데이터를 저장하지 않고, 레시피 추천 요청 때 **필요한 선호 정보만** 함께 받는다.

## 4. 데이터 모델

### 4.1 프로필

```js
{
  id: "p_8f3a...",                 // crypto.randomUUID()
  name: "도경",                     // 1~12자, 프로필끼리 중복 불가
  avatar: "🍳",                    // 고정 이모지 목록 중 선택
  allergies: ["땅콩", "새우"],       // 아래 목록 + 직접 입력
  dietType: "none",                // "none" | "vegetarian" | "vegan" | "pescatarian"
  dislikedIngredients: ["오이"],    // 가능하면 빼 달라고 요청 (알레르기보다 약한 조건)
  spiceLevel: 2,                   // 0 안 매움 ~ 3 아주 매움
  tools: ["프라이팬", "전자레인지"],  // 보유 조리 도구 (없는 도구가 필요한 레시피 지양)
  pantry: ["소금", "후추", "간장"],  // 기본 양념 (2단계 4장의 기본 목록이 초기값)
  defaultServings: 2,
  createdAt: "2026-10-29T05:00:00.000Z",
  updatedAt: "2026-10-29T05:00:00.000Z"
}
```

- 알레르기 선택 목록 (식품 알레르기 표시 대상 기준): 난류(계란), 우유, 메밀, 땅콩, 대두, 밀, 고등어, 게, 새우, 돼지고기, 복숭아, 토마토, 아황산류, 호두, 닭고기, 쇠고기, 오징어, 조개류, 잣. 구현 시 식품의약품안전처의 최신 알레르기 유발물질 표시 대상 목록과 대조해 확정한다.
- 조리 도구 목록: 가스레인지/인덕션, 프라이팬, 냄비, 전자레인지, 오븐, 에어프라이어, 밥솥, 믹서기

### 4.2 저장한 레시피

```js
{
  id: "r_c21e...",
  profileId: "p_8f3a...",
  recipe: { /* 2단계 5.3 형식 레시피 1개 전체 (검증된 것) */ },
  sourceIngredients: ["대파", "두부", "돼지고기"], // 추천받을 때의 냉장고 재료
  memo: "간장 조금 줄이기",          // 0~300자
  rating: 4,                       // 1~5 또는 null
  cooked: true,                    // "만들어 봤어요"
  savedAt: "2026-10-29T05:10:00.000Z"
}
```

같은 프로필 안에서 `recipe.title`과 `steps`가 완전히 같은 레시피는 중복 저장하지 않는다 (♡가 이미 채워진 상태로 표시).

### 4.3 저장 형식

localStorage 키 `fridgeChef.v1` 하나에 저장한다.

```js
{
  version: 1,
  activeProfileId: "p_8f3a...",   // 마지막으로 선택한 프로필, 없으면 null
  profiles: [ /* 4.1 */ ],
  savedRecipes: [ /* 4.2 */ ]
}
```

- `version`은 이후 구조 변경 시 마이그레이션 분기점이다.
- 프로필을 삭제하면 그 프로필의 저장 레시피도 함께 삭제한다 (삭제 전 "저장한 레시피 n개도 함께 삭제됩니다" 확인).

## 5. 레시피 추천에 프로필 반영 (2단계 확장)

### 5.1 API 요청 확장

`POST /api/recipes` 요청에 선택 필드 `preferences`를 추가한다. 프로필이 없으면 보내지 않으며, 그때는 2단계와 똑같이 동작한다.

```js
{
  "ingredients": [...],
  "options": {...},
  "excludeTitles": [...],
  "preferences": {
    "allergies": ["땅콩", "새우"],
    "dietType": "none",
    "dislikedIngredients": ["오이"],
    "spiceLevel": 2,
    "tools": ["프라이팬", "전자레인지"],
    "pantry": ["소금", "후추", "간장"]
  }
}
```

- 프로필 이름 등 추천에 필요 없는 정보는 서버로 보내지 않는다.
- 각 목록은 최대 30개, 항목당 30자, 줄바꿈 제거 (2단계의 프롬프트 주입 방지 규칙과 같음).
- `pantry`가 있으면 2단계 4장의 기본 양념 목록 대신 사용한다.

### 5.2 프롬프트 반영 규칙

| 항목 | 프롬프트 지시 | 강도 |
|---|---|---|
| 알레르기 | "다음 재료와 그 재료가 들어간 가공품은 **절대** 쓰지 마라: 땅콩(땅콩버터 포함), 새우(새우젓 포함)…" | 필수 |
| 식단 유형 | 채식: 고기·생선 금지 / 비건: 동물성 재료 전부 금지 / 페스코: 고기 금지, 해산물 허용 | 필수 |
| 싫어하는 재료 | "가능하면 쓰지 마라" | 선호 |
| 매운맛 | 0~3 단계를 문장으로 설명 | 선호 |
| 조리 도구 | "다음 도구만 있다. 다른 도구가 꼭 필요한 레시피는 피하라" | 선호 |

### 5.3 알레르기 2차 검사 (`lib/allergyCheck.js`)

AI는 지시를 놓칠 수 있으므로 서버에서 한 번 더 검사한다.

1. 레시피의 `usedIngredients`, `missingIngredients`, `seasonings`, `steps` 전체 문자열에서 알레르기 키워드를 찾는다.
2. 키워드는 알레르기별 동의어·가공품 사전으로 확장한다. 예: 새우 → 새우, 새우젓, 건새우 / 대두 → 콩, 두부, 된장, 간장, 두유 / 밀 → 밀가루, 부침가루, 빵가루, 간장(밀 함유 가능) / 난류 → 계란, 달걀, 마요네즈.
3. 걸린 레시피는 버리지 않고 `allergyWarnings: ["새우젓(새우)"]` 필드를 붙여 돌려준다.
4. 화면에서는 해당 카드 맨 위에 빨간 경고 띠를 표시: "⚠ 알레르기 재료(새우)가 들어 있을 수 있어요".
5. 3개 중 2개 이상이 걸리면 1회 재추천을 시도한다.

> 키워드 검사도 완벽하지 않다. 모든 레시피 화면 하단에 "알레르기가 있다면 실제 재료의 성분 표시를 꼭 확인하세요"를 항상 표시한다.

### 5.4 간장·된장처럼 기본 양념이 알레르기에 걸리는 경우

대두·밀 알레르기가 있는 프로필은 기본 양념 목록에서 간장·된장 등을 **자동으로 빼고**, 프로필 편집 화면에 "알레르기 때문에 간장을 기본 양념에서 뺐어요"라고 알려 준다.

## 6. 화면 구성

### 6.1 헤더 프로필 전환

```
┌──────────────────────────────────────────┐
│  🧊 냉장고 셰프        [🍳 도경 ▾] [♡ 12]  │
└──────────────────────────────────────────┘
       ▾ 펼침: 🍳 도경 ✓ / 🥗 엄마 / ➕ 새 프로필 / ⚙ 프로필 관리
```

- 프로필이 하나도 없을 때 첫 화면에 "프로필을 만들면 알레르기를 반영하고 레시피를 저장할 수 있어요 [프로필 만들기] [나중에]" 안내. "나중에"를 고르면 1·2단계 기능은 그대로 쓸 수 있고, ♡를 누를 때 다시 안내한다.
- `[♡ 12]`는 현재 프로필의 저장 레시피 수, 누르면 저장 목록으로 이동.

## 7. 내보내기 / 가져오기

- **내보내기**: 4.3 형식 전체를 `fridge-chef-backup-2026-10-29.json` 파일로 다운로드.
- **가져오기**: JSON 파일 선택 → `version` 확인 → 미리보기("프로필 2개, 레시피 15개") → 방식 선택:
  - **합치기** (기본): `id`가 같은 항목은 건너뛰고 새 항목만 추가. 프로필 이름이 겹치면 "도경 (2)"처럼 이름을 바꿔 추가.
  - **덮어쓰기**: 현재 데이터를 모두 지우고 파일 내용으로 교체 (한 번 더 확인).
- 파일 형식이 틀리거나 필수 필드가 없는 항목은 건너뛰고 "n개 항목을 읽지 못했어요"라고 알려 준다.

## 8. 에러 처리

| 상황 | 동작 |
|---|---|
| localStorage 데이터 손상 (JSON 파싱 실패) | 빈 상태로 시작 + 경고 배너. 손상된 원본은 `fridgeChef.v1.corrupt-<시각>` 키로 옮겨 보관 (덮어써서 잃지 않도록) |
| 일부 항목만 형식 오류 | 그 항목만 버리고 나머지 로드 |
| 저장 실패 (용량 초과, 시크릿 모드) | "저장 공간이 부족해요. 오래된 레시피를 지우거나 내보내기로 백업하세요" 배너, 앱은 메모리 상태로 계속 동작 |
| 프로필 이름 비었음/중복 | 저장 버튼 비활성 + 입력창 아래 안내 |
| 저장된 프로필이 가리키는 `activeProfileId`가 없음 | 첫 번째 프로필로 전환, 없으면 프로필 없음 상태 |
| 가져오기 파일이 JSON이 아님 / `version`이 더 높음 | "이 파일은 읽을 수 없어요" / "더 새 버전 앱에서 만든 파일이에요" |

## 9. 검증 방법

- **단위 테스트** (`node --test`, 순수 함수 대상):
  - `profiles.js`: 이름 공백·중복 거부, 삭제 시 저장 레시피 함께 삭제, 대두·밀 알레르기 → 기본 양념에서 간장 자동 제외
  - `saved.js`: 중복 저장 방지, 검색(공백 무시, 재료·메모 포함), 정렬 3종
  - `store.js`: 손상 데이터 보관 후 빈 상태 시작, 일부 항목 오류 시 부분 로드, 가져오기 합치기/덮어쓰기, 이름 충돌 시 "(2)" 붙이기
  - `allergyCheck.js`: 동의어·가공품 검출 (새우젓 → 새우, 두부 → 대두), 알레르기 없으면 경고 없음, 오탐 사례 확인 (예: "땅콩호박"처럼 이름에 포함된 경우는 경고가 떠도 허용 — 놓치는 것보다 과하게 경고하는 쪽을 택함)
- **수동 체크리스트**:
  - 프로필 2개 만들고 전환 → 저장 목록이 프로필별로 다른지
  - 새우 알레르기 프로필로 해산물 재료 추천 → 새우가 안 나오거나 경고 띠가 뜨는지
  - 비건 프로필 → 계란·우유·고기가 없는 레시피인지
  - 레시피 저장 → 새로고침 → 그대로 있는지
  - 메모·별점 수정 → 새로고침 후 유지
  - 내보내기 → 다른 브라우저에서 가져오기(합치기) → 데이터 일치
  - localStorage를 일부러 깨뜨린 뒤 열기 → 경고 배너 + 원본 보관 키 생성 확인
  - 프로필 없이도 1·2단계가 그대로 동작하는지

## 10. 비기능 요구사항

- 프로필·저장 레시피는 브라우저에만 저장되며 서버로 보내지 않는다 (추천 요청의 `preferences`만 예외).
- 알레르기 정보는 민감할 수 있으므로 서버 로그에 남기지 않는다.
- 저장/삭제는 즉시 반영하고, 삭제는 5초 동안 "되돌리기" 토스트를 제공한다 (확인창 대신).

## 11. 열린 질문 / 후속 과제

- 기기 간 자동 동기화가 필요해지면 로그인과 서버 DB(SQLite 등)를 도입한다. 그때 4장 데이터 모델을 테이블로 그대로 옮길 수 있도록 `id`·`profileId` 구조를 유지해 두었다.
- 장보기 목록(저장 레시피의 부족한 재료 모아 보기)
- 저장 레시피 기반 추천 ("자주 만든 요리와 비슷한 레시피")

## 12. 구현 메모 (2026-10-29)

- 알레르기에 걸리는 **냉장고 재료는 프롬프트에 넣기 전에 서버에서 뺀다** (예: 계란 알레르기면 인식된 계란 제외). 응답의 `excludedForAllergy`로 화면에 "알레르기 때문에 계란은 빼고 추천했어요"를 보여 준다. 다 빠져서 재료가 없으면 `400 ALL_EXCLUDED`.
- 알레르기 경고는 가장 구체적인 키워드로 보여 준다 (예: "새우"보다 "새우젓(새우)").
- 저장할 때 `allergyWarnings`는 빼고 저장한다 (추천 당시 프로필 기준 정보라서).
- 알레르기 목록 19종은 식약처 최신 표시 대상 목록과 아직 대조하지 않았다.
